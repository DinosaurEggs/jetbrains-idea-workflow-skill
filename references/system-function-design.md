# 系统功能详细设计格式

## 使用边界

只在用户要求系统功能设计或系统详细设计时使用本文件。所有影响设计的事实和选择先按 [core-workflow.md](core-workflow.md)
与 [design-first.md](design-first.md) 处理；不得用假设、“待定”占位、空栏目、推荐方案或留到开发阶段确认的内容补齐正文。系统功能设计与开发计划相互独立，完成本正文后不自动生成开发计划或进入代码修改。

仍有影响设计的事项未确认时，只提出对应问题并结束当前轮，不输出部分正文。方向已经明确时，正文直接陈述确定的系统行为、规则和边界，不保留候选方案或选择建议。

一旦进入系统功能设计正文，必须使用下列固定结构，不得改写为自定义章节、通用产品建议或功能清单。缺少使用主体、权限、输入输出、业务规则、状态、界面或数据等必要事实，且无法从项目证据查明时，按核心状态机提问；不得用行业惯例、常见做法或自行扩展的角色、字段、操作和异常分支补齐。

## 固定正文

```text
1. 系统概述

[存在业务流程时]
1.1 业务流程及流程图
<业务流程说明>
<业务流程图>

2. 系统设计
2.1 <功能模块>
功能描述：
<功能描述>

[存在界面时]
界面：
<界面说明或界面简图>

[存在处理规则时]
处理：
- <操作、状态或步骤>：<处理规则>

[存在数据库设计时]
3. 数据库设计
<数据库设计说明>
```

代码块只表示结构，实际正文使用 Markdown 正常输出，不用代码块包裹全文。方括号行只表示适用条件，实际输出时删除。系统设计直接按功能结构排列，不按用户角色、客户端或后台端分组；已有父子功能结构时使用
`2.x`、`2.x.y`，只在最末级功能下填写内容。

## 内容要求

### 系统概述

- 说明设计范围、触发与前置条件、主流程、关键分支和结束结果。
- 存在业务流程时提供逐步说明和 ASCII 流程图；文本回复不使用 Mermaid。没有流程内容时省略该小节。
- 只使用项目证据或用户已确认的业务事实。

### 系统设计

每个最末级功能必须包含“功能描述”；“界面”和“处理”仅在确有内容时输出：

- 功能描述：说明目标、使用主体、权限、前置条件、输入、输出和边界。
- 界面：说明入口、区域、字段、按钮、状态和反馈；新增界面使用 ASCII 简图。
- 处理：按操作、状态或步骤说明触发、校验、权限、核心处理、数据变化、外部调用、返回和异常。接口契约、配置变化和必要伪代码放入对应处理项。

### 数据库设计

只有实际涉及数据库设计时才输出该章节，并说明现有结构、受影响表、字段、关系、索引、约束、迁移和适用的回滚方案。需要提供或执行 SQL 时遵守 [database-sql.md](database-sql.md)；提供 SQL 不代表获准执行。

## 完整性检查

- 始终保持“系统概述、系统设计”的顺序；数据库设计仅在适用时置于其后。
- 正文使用固定功能结构，不用角色列表、功能清单、建议列表或自由章节替代“系统概述、系统设计”和最末级功能内容。
- 存在业务流程时包含逐步说明和 ASCII 流程图；存在界面时包含入口、区域、字段、按钮、状态、反馈及必要的 ASCII 简图。
- 每个使用主体、权限、字段、按钮、状态转换、处理规则、异常和数据设计都能追溯到项目证据或用户已确认事实，不用通用经验补齐。
- 正文只使用确定陈述，不保留推荐、建议、可考虑、暂定或留到后续阶段决定的设计内容。
- 用户继续修改系统功能设计时按 [design-first.md](design-first.md) 的“正文修订”规则更新正文并等待确认；正文呈现最终状态，必要的业务边界、兼容要求和风险约束仍须保留。
- 候选选择只确认设计方向；输出详细设计后，只有用户明确要求按当前设计实施，才可进入代码、配置、SQL 或其他文件修改。
- 可选栏目无内容时直接省略，不输出空标题、“无”或“不涉及”。无法确定是否适用时按核心状态机询问。
- 区分现状事实和拟议变更，核对前后端字段、状态、权限、异常、数据库和配置的一致性。
- 不复制示例文档中的项目、组织、人员、角色、功能、界面或数据库内容。
