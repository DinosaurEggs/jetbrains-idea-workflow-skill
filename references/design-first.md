# 设计先行

## 适用条件

以下任务进入设计先行流程：

- 用户明确要求方案、系统功能设计或详细设计。
- 变更跨越多个模块、前后端或外部系统。
- 调整公共接口、数据库契约、公共组件、设计系统或核心业务流程。
- 新功能包含多个业务步骤、状态、权限、数据变化或存在实质不同的实现方向。
- 影响范围、可逆性、兼容性或失败成本要求先评估方案。

需求和项目约定已经唯一确定、影响局限于单个实现点的字段、校验、文案、样式或小型功能，不因“新增”二字自动进入完整设计流程；仍须完成必要上下文查证和影响检查。

## 设计流程

1. 完成适用的源码、配置、文档和数据库只读查证。
2. 按 [core-workflow.md](core-workflow.md) 解决所有影响设计的待定事项。
3. 向用户提供调整或实现方案时，至少给出两个可选方案，比较实际差异、影响和风险，给出建议并等待用户选择。
4. 方案确定后形成足以实施和验收的详细设计，并等待用户明确确认。
5. 方案选择、详细设计及相关业务事项全部确认后才能编码。

不得虚构不可行的技术方案。项目约束只能支持一种技术实现时，将保持现状、缩小范围或分阶段实施作为备选方案，并说明限制。用户初始请求已经提供完整、唯一且可实施的设计并明确要求实现时，可以视为对应方案和范围已经确认；发现缺口时仍按核心确认状态机处理。

## 方案比选

只比较真正影响选择的内容，例如：

- 变更范围和兼容性。
- 数据、接口和迁移影响。
- 权限、安全、事务和一致性。
- 维护成本、扩展能力和验证成本。
- 上线、回滚和残余风险。

不要为每个候选方案重复完整详细设计，也不要把推荐方案作为未回答事项的默认选择。

## 详细设计

需要系统功能设计或固定详细设计正文时，读取 [system-function-design.md](system-function-design.md)。纯重构、依赖调整或其他不属于系统功能设计的任务，按实际影响给出针对性设计，不强制套用固定正文。

用户只要求设计时，以确认范围内的设计正文作为任务结果，不主动进入实现。
