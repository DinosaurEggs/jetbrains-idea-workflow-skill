# 工程开发计划格式

## 使用边界

本 skill 中的工程开发计划用于规定已经确定的系统行为如何通过代码、页面、接口、数据、SQL、可执行配置或测试实现。只在目标系统行为和验收边界已经由用户指令、已确认系统功能详细设计或项目证据唯一确定时使用本文件。

适用范围包括行为已经确定的新功能、按钮和交互，以及 Bug 修复、重构、性能优化、依赖调整和不改变既定功能行为的技术改造。

必要查证后仍存在会改变业务规则、主流程、关键分支、状态转换、使用主体、角色权限、输入、输出、异常或用户反馈的待定设计时，不使用本文件，先输出系统功能详细设计。仅存在不改变目标系统行为的技术实现选择时，仍使用工程开发计划。

开始正文前，解决所有会改变工程范围、核心实现、接口、数据、权限或验证结果的事实和选择。

## 正文规模

同时满足以下条件时使用精简计划：

- 变更只实现一个已经确定的目标行为，且涉及的模块、文件和关键符号能够在计划中完整列明；
- 不改变公共接口、数据库结构、权限、事务、依赖、运行环境或跨模块契约；
- 不包含需要图示才能准确说明的界面布局、状态转换或业务分支。

精简计划依次包含：

1. 开发目标与范围。
2. 文件与符号变更。
3. 核心实现逻辑。
4. 验证与验收。

不满足精简条件时使用完整计划，依次包含：

1. 开发目标与范围。
2. 代码变更。
3. 核心实现逻辑。
4. 界面设计，仅在存在需要说明的布局或交互关系时使用。
5. 业务流程，仅在存在多步骤、分支或状态转换时使用。
6. 关联影响，仅在涉及接口、数据库、权限、事务、租户、缓存、异步、配置或兼容性时使用。
7. 验证与验收。

不适用的条件章节直接省略并连续调整编号，不输出空标题、“无”或“不涉及”。

## 内容要求

### 开发目标与范围

说明当前行为、已经确定的目标系统行为和验收边界、开发目标、包含范围、排除范围和必须保持不变的业务或兼容行为。范围必须来自当前项目证据、用户指令或已确认系统功能详细设计，不得在本节新增未经确认的业务规则。

### 文件与代码变更

按模块和文件列出关键符号或区域、职责及新增或修改内容。精简计划可以使用分项说明；完整计划使用“模块或文件、符号或区域、新增或修改、变更内容”四列的表格。

只覆盖完成目标所需的前端、后端、类型、持久化、配置和测试文件。实施时发现需要实质扩大文件、符号、行为、接口、数据、权限、风险或验收范围，停止依赖新增范围的修改，更新完整工程开发计划并重新取得确认和实施授权。

### 核心实现逻辑

按功能链或代码单元说明触发、输入、前置条件、校验、权限、处理、状态或数据变化、输出和异常。实现逻辑必须对应已经确定的目标系统行为和验收边界，不得通过技术实现新增、替换或弱化业务规则。优先复用项目已有组件、服务、类型和工具；只有文字不足以准确表达算法、契约或状态转换时才提供必要伪代码。

### 界面设计

说明页面入口、区域、字段、按钮、状态、反馈和响应式行为。只有布局关系无法通过简短文字唯一表达时才提供 ASCII 简图或用户要求的其他图示。

### 业务流程

只在理解代码变更、接口协作或验收条件确有需要时，按实际顺序复述已经确定的入口、操作、状态和关键分支，不在本节新增或选择业务规则。发现必须重新确定目标系统行为时，停止工程开发计划，转入系统功能详细设计。

### 关联影响

只说明实际涉及的接口、类型、数据库、事务、权限、租户、缓存、异步、配置、调用方和兼容性。需要提供 SQL 时继续应用 `数据库SQL与持久化层.md`
；开发计划不构成数据库执行授权。

### 验证与验收

列出能够验证本次变更的文件级检查、目标测试或运行入口，以及正常、异常和边界验收条件。文件级闭环按 `编辑格式化与文件级检查.md`
处理；非文件级执行按 `非文件级执行与验证.md` 判断授权。计划中的验证项不构成执行许可。

## 完整性要求

计划中的文件范围、核心实现逻辑、界面或已确认业务流程、关联影响和验收条件必须相互一致。正文只使用项目证据、用户指令和已确认系统功能详细设计，不保留候选项、占位文字、未解决的目标系统行为或待实施决定。
